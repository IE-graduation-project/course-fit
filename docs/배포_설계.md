# 배포 설계 — API 서버 · 컨테이너 · 호스팅

> 프론트(`web/`)는 Vercel에 떠 있으나 정적 픽스처로 구동 중이고, 추천 엔진은 로컬 CLI로만 돈다.
> 이 문서는 둘을 잇는 **HTTP API 서버를 만들고 컨테이너로 감싸 무료 호스팅에 올리는** 과정의
> 설계를 정리한다. 계약 스펙은 `docs/API_계약.md`(이미 확정), 이 문서는 **그 계약을 구현·배포하는
> 방법**을 다룬다. 검토·기각한 선택지와 근거를 함께 남긴다.
>
> 확정일 2026-09-13. 선행 문서: `API_계약.md`, `ILP_추천시스템_설계.md`, `시스템_한계.md`.

## 0. 배경 — 현재 상태

| 구성요소 | 상태 |
|---|---|
| 데이터 파이프라인 (크롤 → LLM 매핑 → CSV) | 완료. `data/*.csv` 8종 |
| DB (`db/app.db`, SQLite) | 완료. course 3,389 · course_section 927 · course_competency 33,890 |
| 추천 엔진 (`recommender/`) | 완료. CLI로 동작, 테스트 68개 통과 |
| 성적표 파서 (`transcript/`) | 완료 (텍스트 트랙). PDF는 인터페이스만 |
| 프론트 (`web/`) | 완료. Vercel 프로덕션 배포됨 |
| **HTTP API 서버** | **없음.** repo 전체에 FastAPI/Flask 코드 부재 |

프론트는 `NEXT_PUBLIC_API_BASE`가 비어 있어 `public/fixtures/`의 정적 JSON을 읽는다.
따라서 **누가 어떤 성적표를 넣어도 결과가 고정**이다. 이 문서의 목표는 그 한 칸을 채우는 것.

### 0.1 설계 중 발견한 결함 2건

설계를 확정하는 과정에서 기존 코드·데이터의 결함 두 가지가 드러났다. 둘 다 픽스처 모드에서는
증상이 없다가 **실 API를 붙이는 순간 문제가 되는** 종류라 여기 명시해 둔다.

1. **픽스처를 생성한 학생이 DB에 없다.** 값 대조 검증이 불가능해 검증 전략을 바꿨다 → §3.1
2. **프론트에 학과·입학년도 입력 UI가 없다.** `web/app/start/page.tsx:46`이 `dept: "BIZ"`,
   `admissionYear: 2022`를 **하드코딩**한다. 픽스처 모드에서는 이 값이 무시되므로 무해했으나,
   실 API가 붙으면 **모든 사용자가 경영 2022로 적재된다.** 산업데이터공학과 학생이 성적표를
   넣어도 경영학과 졸업요건으로 진단이 나가고, 에러조차 나지 않는다. `need_g`는 ILP의 2순위
   목적함수이므로 진단 화면만이 아니라 **추천된 시간표 자체가 틀린다.** → 결정 ⑨, Phase 1 스텝 6.5

### 0.2 목표와 비목표

**목표** — 졸업작품 데모로 쓸 수 있는 공개 URL. 실제 성적표를 넣으면 실제 ILP가 풀린다. 비용 0원.

**비목표** — 고가용성, 수평 확장, 영구 데이터 보관, 로그인/계정. 데모 규모(동시 수 명)를 전제한다.

### 1.2 요청 하나가 흐르는 경로

```
학생이 성적표 붙여넣기
   │
   ├─ POST /api/transcript {text, dept, admissionYear}
   │     parse_transcript_text()  → TranscriptResult (input_hash 결정적 해시)
   │     load_transcript(conn)    → student / student_course 적재 (idempotent)
   │     ← {studentId, courseCount, matchedCount}
   │
   └─ POST /api/recommend {studentId, job, mode}
         data.load_student / load_candidates / load_rho / load_min_credits
         params.compute_sigma → σ_k = 1 − exp(−α·Σ gf·w)
         params.compute_gap   → gap_k = max(0, ρ_k − σ_k)
         params.score_of      → Score_c = Σ_k gap_k·w_{c,k}
         params.compute_need  → need_g = max(0, min_credits_g − 기이수_g)
         model.solve_topk     → 2단계 lexicographic ILP (CBC), k-best
         serialize.build_payload
         ← 계약 JSON (시간표 · 진단 · 근거)
```

**계산 로직은 한 줄도 새로 짜지 않는다.** API는 위 함수들을 순서대로 부르는 껍데기다.

### 1.3 데이터 저장 전략 — SQLite는 서버가 아니다

RDS 같은 관리형 DB와 근본적으로 다른 점을 명시해 둔다.

| | RDS 방식 | 우리 방식 |
|---|---|---|
| DB의 실체 | 별도 호스트에서 도는 **프로세스** | 컨테이너 안의 **파일 하나** (3.6MB) |
| 접근 | TCP + 호스트/계정/비번 | `sqlite3.connect(path)` = 파일 open |
| 배포 시 할 일 | 인스턴스 생성 · 보안그룹 · 마이그레이션 | 없음 (이미지에 들어 있음) |
| 비용 | 시간당 과금 | 0 |

따라서 "DB를 어디에 호스팅하나"라는 질문이 성립하지 않고, **"이 파일을 컨테이너에 어떻게 넣나"**로 바뀐다. 답은 **빌드 타임 생성**이다.

```dockerfile
COPY data/ ./data/
COPY db/   ./db/
RUN python db/ingest.py --reset      # 이미지 레이어에 app.db 가 포함됨
```

`data/*.csv`가 git에 있으므로 어디서 빌드해도 동일한 DB가 재현된다.

#### 읽기/쓰기 분리

무료 호스팅에는 영구 디스크가 없다(재시작 시 초기화). 우리 DB는 성격이 둘로 갈린다.

```
읽기 전용 시드 (이미지에 구움)          쓰기 (기동 시 /tmp 로 복사)
├ course            3,389              ├ student
├ course_section      927              └ student_course
├ course_competency 33,890
├ job_competency        60
└ graduation_requirement 20
```

`api/db.py`가 기동 시 1회 시드를 `/tmp/app.db`로 복사하고, 서버는 그 사본만 연다.
환경변수 `COURSE_FIT_SEED_DB`(읽기전용 원본) / `COURSE_FIT_DB`(열 경로)로 제어하며,
둘 다 미지정이면 `db/app.db`를 직접 쓴다(로컬 개발).

**결과**: 재시작하면 학생 데이터가 사라진다. 데모에서는 의도된 동작이며 §6에서 다시 다룬다.

## 2. API 서버 설계

### 2.1 모듈 구성

```
api/
  __init__.py
  main.py        FastAPI 앱 · 라우팅 · CORS · 예외→HTTP 매핑 · 기동 훅
  schemas.py     요청 pydantic 모델 (응답은 dict — 계약 정본이 web/lib/types.ts 라 이중관리 회피)
  serialize.py   Recommendation → 계약 JSON.  ★ dump_fixtures.py 로직 이관 (결정 ①)
  db.py          DB 경로 해석 · 시드 복사 · TTL 정리
requirements-api.txt   fastapi · uvicorn · pulp  (런타임 의존성만)
tests/test_api.py
```

**기존 모듈(`recommender/`, `transcript/`)은 건드리지 않는다.** 단 하나의 예외가 결정 ⑤.

#### 런타임 의존성 분리

현재 `requirements.txt`에는 sentence-transformers·selenium·pandas·openai 등이 섞여 있으나,
이들은 **전부 오프라인 전용**이다. 실측 확인: `recommender`·`transcript`가 import하는 외부
패키지는 `pulp` 하나뿐이고 나머지는 표준 라이브러리(`sqlite3`, `re`, `math`, `hashlib`)다.

```
requirements-api.txt  →  fastapi · uvicorn[standard] · pulp     (이미지 ≈ 120MB)
requirements.txt      →  기존 그대로 (크롤·매핑·분석용)
```

### 2.2 엔드포인트

| 메서드 | 경로 | 요청 | 응답 |
|---|---|---|---|
| GET | `/health` | — | `{status, courses, sections, db}` 배포 확인용 |
| GET | `/api/reference` | — | jobs 6 · competencies 10 · modes 3 · areas · **programs**(결정 ⑨) |
| POST | `/api/transcript` | `{text, dept, admissionYear}` | `{studentId, deptId, admissionYear, courseCount, matchedCount, semesters: []}` |
| POST | `/api/recommend` | `{studentId, job, mode?, eps?, maxCredits?, minCredits?, topK?}` | 계약 payload 전체 |

응답 스키마 전문은 `docs/API_계약.md` §1~3, 타입 정본은 `web/lib/types.ts`.

### 2.3 설계 결정

#### ① 직렬화 로직의 단일 원천 — `api/serialize.py`

**문제**: 계약 JSON을 만드는 코드가 지금 `web/scripts/dump_fixtures.py`에 있다. API도 같은
스키마를 내야 하는데, 두 벌로 두면 반드시 어긋난다(한쪽에 필드를 추가하고 다른 쪽을 잊는다).

**결정**: 로직을 `api/serialize.py`로 이관하고 `dump_fixtures.py`는 그것을 import만 한다.
픽스처와 실 API 응답이 **같은 코드에서 나오는 것이 구조적으로 보장**된다.

**부수 결정 (②) — section 메타를 DB에서 읽는다.** `dump_fixtures.py`는 `professor`/`timeRaw`/
`offeringDept`/`category`를 `data/course_section.csv`에서 직접 읽는다. 컨테이너에 CSV를 넣지
않기 위해 `course_section` 테이블에서 읽도록 바꾼다. 네 컬럼 모두 DB에 존재하며 값 일치를
확인했다(`311317-1` → 안형준 / 화234 / 경영학전공 / 전선).

#### ③ dept·입학년도 검증을 `/api/transcript`로 앞당긴다

**문제**: 적용 가능한 졸업요건이 없는 학과·입학년도를 넣어도 성적표는 정상 적재되고,
**추천 단계에 가서야** `load_min_credits`가 `ValueError`를 던진다. 사용자는 성적표를 다
붙여넣고 다음 화면에서 에러를 만난다.

**결정**: `/api/transcript`에서 결정 ⑨의 규칙으로 미리 검증하고, 적용할 요건이 없으면 400과
함께 "산업데이터공학과는 2026학번부터 지원합니다" 형태의 메시지를 돌려준다. 실패를 입력
시점으로 당긴다.

#### ⑤ CBC 풀이 시간 상한 — 기존 코드 수정 2곳 중 하나

**문제**: `model.py`의 `PULP_CBC_CMD(msg=msg)`에 시간 제한이 없다. 로컬 실측은 0.6초(538변수)지만,
탐색이 폭발하는 입력이 오면 요청이 무한정 물린다. 웹 서버에서는 허용할 수 없다.

**결정**: `solve_topk`/`solve`에 `time_limit: float | None = None`를 추가하고 `PULP_CBC_CMD`에
전달한다. 기본값 `None`은 현재 동작과 동일하므로 기존 테스트 68개에 영향이 없다. API에서는 30초를 준다.

**기각한 대안**: asyncio 타임아웃으로 감싸기 → CBC는 서브프로세스라 파이썬 레벨 취소가
프로세스를 안 죽인다. 좀비가 남는다.

(기존 코드 수정의 나머지 한 곳은 결정 ⑨의 `data.py:load_min_credits`다.)

#### ⑥ 동시성

uvicorn 워커 2개. CBC는 서브프로세스라 GIL과 무관하게 병렬로 돈다. SQLite 쓰기 락은
`sqlite3.connect(timeout=10)`으로 방어한다. 데모 규모에서 충분하며, 늘려야 할 근거가 생기면
워커 수만 올린다.

#### ⑦ CORS

환경변수 `COURSE_FIT_CORS_ORIGINS`(콤마 구분). 기본값은 Vercel 프로덕션 + `localhost:3000`.

#### ⑧ TTL 24시간 자동 삭제

§6에서 다룬다.

#### ⑨ `admission_year` = "적용 시작 연도" (effective-from)

**문제**: `graduation_requirement`에는 `IDE 2026`과 `BIZ 2022` 두 벌만 있고,
`load_min_credits`가 **정확 매칭**(`WHERE dept_id=? AND admission_year=?`)을 한다. 그래서
경영 2023학번은 요건을 못 찾아 거부된다 — 실제로는 2022 교육과정이 그대로 적용되는데도.

**사실 확인**(2026-09-13, 졸업 책자 대조): 경영학과는 **2022 교육과정이 22학번부터 계속
적용**된다. 산업데이터공학과 2026 교육과정은 **26학번부터** 적용되며, 그 이전 학번은 지원
대상이 아니다(신설 교육과정 기준으로 서비스한다는 방침).

**결정**: `admission_year`를 "그 연도 입학생만"이 아니라 **"그 연도부터 다음 개정 전까지
적용"**으로 해석한다. 쿼리를 바꾼다.

```sql
SELECT area, min_credits FROM graduation_requirement
WHERE dept_id = ? AND min_credits IS NOT NULL
  AND admission_year = (SELECT MAX(admission_year)
                        FROM graduation_requirement
                        WHERE dept_id = ? AND admission_year <= ?)
```

| 학생 | 적용되는 요건 | 판정 |
|---|---|---|
| 경영 2022~2026학번 | BIZ 2022 | 정상 |
| 경영 2021학번 이하 | 없음 | 거부 (2022 개정 이전) |
| 산데공 2026학번 이상 | IDE 2026 | 정상 |
| 산데공 2025학번 이하 | 없음 | 거부 — **"26학번부터 지원"이 데이터 구조로 표현된다** |

이는 임시방편이 아니라 대학의 실제 규칙(교육과정 개정 연도 기준 적용)을 구현한 것이다.
2028 개정판이 나오면 CSV에 10행을 추가하는 것만으로 반영된다.

**파급**:
- `db/schema.sql`·`data/README.md`의 `admission_year` 주석을 "적용 시작 입학년도"로 정정한다.
  지금 주석("입학년도")은 새 해석과 어긋나 다음 사람을 오도한다.
- `/api/reference`에 지원 범위를 싣는다. 연도 목록이 아니라 시작 연도다.
  ```json
  "programs": [
    {"dept": "IDE", "name": "산업데이터공학과", "fromYear": 2026},
    {"dept": "BIZ", "name": "경영학과",        "fromYear": 2022}
  ]
  ```
  프론트는 `fromYear ~ 현재 학년도`로 드롭다운을 채운다. 연도가 늘어도 **프론트 수정이 필요 없다.**
- 결과 화면에 **적용 기준을 고지한다** — "2022학년도 교육과정 기준". 2025학번 경영 학생이
  자기 기준이 맞는지 확인할 수 있고, 무엇을 근거로 계산했는지 드러난다.
- 기존 테스트는 영향받지 않는다. 정확 매칭 케이스(2022/2026)는 `admission_year <= 자기자신`이
  항상 성립하므로 같은 결과가 나온다.

### 2.4 에러 → HTTP 코드 매핑

| 상황 | 코드 | 근거 |
|---|---|---|
| `studentId` 없음 | 404 | |
| `job` 없음 / dept·year 조합 무효 | 400 | |
| 성적표에서 0과목 파싱 | 400 | 조용히 빈 결과를 주면 사용자가 원인을 모른다 |
| **ILP infeasible** | **200** + `timetables: []` | 계약 명시. 500은 "서비스 고장", 빈 결과는 "조건이 빡세다" — 메시지가 달라야 한다. 프론트에 전용 화면이 있다 |
| 그 외 | 500 | |

infeasible일 때만 최상위에 `solverStatus`를 덧붙인다(디버깅용). Optimal일 때 넣지 않는 이유는
픽스처와의 스키마 동일성을 깨지 않기 위해서다.

## 3. 검증 전략 — "프론트가 안 깨진다"를 어떻게 증명하나

### 3.1 픽스처 정합성 문제 (발견)

당초 계획은 "실 API 응답이 기존 픽스처 18개와 값까지 일치하는지 대조"였다. **불가능함을 확인했다.**

픽스처를 생성한 학생이 DB에 없다.

| | 픽스처 | 현재 DB |
|---|---|---|
| 학생 | BIZ 2022, `746696b793744f17` | `8c4b505bb386a0c0`(BIZ 2022) 외 2명 |
| `need` | `{SW데이터활용역량:9, 전공선택:12, 특성화교양:3}` | `{…전공선택:21, 전공필수:18, 공통교양:15…}` 8개 영역 |

`transcripts/`의 txt 4개를 재파싱해도 나오는 해시는 `412813643e89d53f` · `8c4b505bb386a0c0` ·
`63b5a4888b5aa035` · `097725a127e343b4` — `746696b793744f17`은 없다.
6월 `db/ingest.py --reset` 실행 시 student 테이블이 소거됐고(치트시트에 ⚠️로 기재됨) 원본 성적표도
남아 있지 않다.

### 3.2 대체 전략 — 2단 검증

**(1) 스키마 대조** — 픽스처 JSON에서 *구조*(키 집합 · 중첩 · 타입 · 역량 10축 완전성)를 추출해
실 API 응답과 비교한다. 값은 학생이 다르니 당연히 다르지만, **모양이 같으면 프론트는 안 깨진다.**
프론트가 실제로 읽는 필드 목록이 `docs/API_계약.md`에 표로 있으므로 이를 체크리스트로 쓴다.

**(2) 값 회귀** — 현재 학생 해시로 뽑은 응답을 golden 파일로 저장한다. 이후 매핑·솔버·직렬화를
건드렸을 때 값이 바뀌는지 감지한다.

**예외 — `/api/reference`는 값까지 대조한다.** 학생과 무관한 정적 데이터라 §3.1의 문제를 겪지
않는다. 기존 `fixtures/reference.json`의 **모든 키와 값이 일치**해야 하며, 결정 ⑨의 `programs`만
신규 키로 허용한다(추가는 프론트를 깨지 않는다). 계약이 맞다는 첫 실증이 이 대조다.

### 3.3 추천 로직 불변식 검증

응답 JSON만 보고 ILP 제약 위반을 잡아낸다.

- 총학점 ∈ [`minCredits`, `maxCredits`]
- 같은 슬롯이 두 번 등장하지 않음 (A1 시간충돌)
- 한 과목당 분반 1개 (A2)
- 기수강 과목 미포함 (B1)
- `careerReason[].share` 합 ≈ 1

### 3.4 엔드투엔드

성적표 텍스트 → `/api/transcript` → 받은 `studentId`로 → `/api/recommend` → 시간표에 과목이 실제로
들어 있는지. 추가로 같은 학생에 `DA`와 `MKT`의 결과가 **실제로 다른지** 확인한다(룩업이 아니라
매 요청 ILP를 푸는 중임의 증명).

### 3.5 픽스처의 지위 변경

API가 생기면 픽스처의 원래 목적("백엔드 없이 프론트 구동")은 소멸한다. 다만 셋은 남는다.

1. **프론트 로컬 개발** — Docker·파이썬·DB 없이 `npm run dev`만으로 화면이 뜬다
2. **스키마 대조 테스트의 기준** (§3.2)
3. **발표 당일 폴백** — `NEXT_PUBLIC_API_BASE`를 지우고 재배포하면 1분 내 복귀

비용은 없다. `public/`의 정적 파일이라 JS 번들에 포함되지 않고, API 모드에서는 fetch 자체가
일어나지 않는다.

**단 썩은 상태로 두지 않는다.** Phase 1.5에서 `transcripts/transcript_text_yeongjun.txt`
(40과목, BIZ 2022, 해시 `412813643e89d53f`)를 적재해 재생성한다. 결정 ① 이후이므로 재생성
시점부터 픽스처 = 실 API 응답이 코드 수준에서 보장된다. 현재 DB의 BIZ 학생(13과목)보다 σ가
풍부하고 학과·학번이 원 픽스처와 같아 화면 품질이 유지된다.

## 4. 컨테이너

```dockerfile
FROM python:3.12-slim
WORKDIR /app
COPY requirements-api.txt .
RUN pip install --no-cache-dir -r requirements-api.txt
COPY data/ ./data/
COPY db/ ./db/
COPY recommender/ ./recommender/
COPY transcript/ ./transcript/
COPY api/ ./api/
RUN python db/ingest.py --reset          # 빌드 타임 DB 생성
ENV COURSE_FIT_SEED_DB=/app/db/app.db  COURSE_FIT_DB=/tmp/app.db
EXPOSE 7860
CMD ["uvicorn", "api.main:app", "--host", "0.0.0.0", "--port", "7860", "--workers", "2"]
```

- **7860 포트**는 Hugging Face Spaces 규약이다.
- **CBC 바이너리**: pulp가 플랫폼별로 번들한다(linux/i64 7.0MB, arm64 7.5MB). 별도 설치 불필요.
  단 실행 권한과 `/tmp` 쓰기가 필요하다 — 읽기전용 파일시스템 환경에서는 여기서 실패한다.
- 예상 이미지 크기 ≈ 120MB (python-slim + pulp 36MB + fastapi + app.db 3.6MB).

## 5. 호스팅 선택

### 5.1 제약

| 요구 | 이유 |
|---|---|
| 네이티브 바이너리 실행 | CBC 솔버 |
| `/tmp` 쓰기 | CBC 임시 LP 파일 + SQLite INSERT |
| 메모리 512MB | 538변수 ILP |
| HTTPS | Vercel(https)에서 호출하므로 mixed content 차단 회피 |

### 5.2 채택: Hugging Face Spaces (Docker SDK)

| | 카드 | 잠들기 | 비고 |
|---|---|---|---|
| **HF Spaces** ★ | 불필요 | 48시간 무활동 | 2 vCPU / 16GB, Dockerfile 그대로, HTTPS 자동 |
| Google Cloud Run | 필요 | 요청 없으면 0 (콜드스타트 2~5초) | 무료 한도 넉넉, 가장 정석 |
| Render 무료 | 불필요 | **15분** → 콜드스타트 ~50초 | 발표 중 멈추면 치명적 |

**채택 근거**: 카드 등록이 불필요하고, 15분이 아니라 48시간 기준이라 발표 전날 한 번 띄워두면
당일 확실히 살아 있다. Render의 50초 콜드스타트는 발표장에서 감수할 수 없는 위험이다.

**기각: Cloudflare Workers** — V8 아이솔레이트라 네이티브 바이너리 실행도 서브프로세스도 불가능하다.
Python Workers도 Pyodide(WASM) 기반이라 CBC를 못 돌린다. Cloudflare Containers는 유료 플랜 전제.
(프론트를 Pages로 옮기는 것은 가능하나 Vercel에서 옮길 이유가 없다.)

**기각: Vercel Python Functions** — 프론트와 같은 플랫폼이라는 이점은 있으나, Lambda 기반이라
번들 크기·바이너리 실행 권한·함수 타임아웃이 모두 불확실하다. 데모 일정에 불확실성을 넣지 않는다.

**이전 가능성**: Dockerfile이 같으므로 Cloud Run 등으로 옮겨도 비용이 들지 않는다.

## 6. 개인정보 처리

로그인을 두지 않는다. 수강신청 기간에 한 번 쓰는 도구인데 가입을 요구하면 대부분 이탈하고,
계정·비밀번호·세션이라는 보안 책임 자체가 생기지 않는 편이 낫다.

### 6.1 구조적 사실

- **학번·성명은 수집 자체가 불가능하다.** 클래스넷 '전체성적조회' 화면에 해당 정보가 없어
  파서가 가져올 수 없다(`transcript/parse_text.py` 모듈 독스트링).
- 학생 식별자는 `input_hash` — 성적표 내용의 결정적 해시(16자 hex)다. 계정이 아니다.
- 컨테이너 재시작 시 `/tmp`의 학생 데이터가 소멸한다.

### 6.2 결정 ⑧ — TTL 24시간

"세션 동안만 존재한다"는 표현은 부정확하다. 실제로는 **컨테이너가 사는 동안**이고, HF 무료
Space는 48시간 무활동 전엔 잠들지 않으므로 성적표가 며칠 남을 수 있다. 발표에서 정확하지 않은
주장을 하지 않기 위해, **말을 바꾸는 대신 구조를 말에 맞춘다.**

`/api/recommend` 호출 시마다 24시간 지난 `student` / `student_course` 행을 삭제한다(쿼리 2줄).
그러면 다음 진술이 **사실이 된다**:

> 로그인이 없어 계정 정보를 일절 수집하지 않습니다. 성적표는 추천 계산에만 쓰이고 24시간 내
> 자동 삭제되며, 서버 재시작 시에도 사라집니다. 학번·이름은 애초에 파싱 대상이 아닙니다.

`/start` 화면에 고지 한 줄을 추가한다: "붙여넣은 성적표는 추천 계산에만 쓰이며 24시간 후 자동
삭제됩니다."

### 6.3 남는 한계 (정직하게)

`input_hash`를 아는 사람은 누구나 해당 성적표 기반 추천을 조회할 수 있다. 16자 hex라 추측은
어렵지만, URL에 실려 공유되면 노출된다. 실사용자 규모가 커지면 서명된 단기 토큰으로 바꿔야 한다.

## 7. 배포 절차

매 스텝이 독립적으로 검증되고 커밋 가능해야 한다. 스텝마다 "무엇으로 끝났음을 아는가"를 둔다.

### 7.1 Phase 1 — API 서버

| 스텝 | 내용 | 완료 판정 |
|---|---|---|
| 1 | `api/serialize.py` 추출 · section 메타를 DB 조회로 (①②) | 이관 전/후 JSON이 바이트 단위로 동일 |
| 2 | `api/db.py` + `/health` | `curl /health` → `courses: 3389, sections: 927` |
| 3 | `GET /api/reference` + `programs` (⑨) | `fixtures/reference.json`과 값까지 일치 (§3.2 예외) |
| 3.5 | `data.py:load_min_credits` 쿼리 교체 + 스키마 주석 (⑨) | 경영 2023 → BIZ 2022 적용 · 산데공 2025 → 거부 |
| 4 | `POST /api/transcript` + 조기 검증 (③) | yeongjun 전체 성적표 → `412813643e89d53f` · 무효 조합 400 |
| 5 | `POST /api/recommend` + `time_limit`(⑤) + TTL(⑧) | 스키마 대조 · 불변식(§3.3) · `DA ≠ MKT` |
| 6 | `requirements-api.txt` 분리 · 테스트 정리 | 기존 68개 + 신규 통과 · 깨끗한 환경에서 기동 |
| 6.5 | `/start`에 학과·입학년도 선택 UI · 결과 화면 기준 고지 (⑨, §0.1 ②) | 하드코딩 제거 · 두 학과 모두 정상 동작 |
| 7 | 픽스처 재생성 (§3.5) | 픽스처 18개 = 실 API 응답 |

3.5는 1~3과 독립이라 순서를 당겨도 된다. 먼저 해두면 4·5의 검증이 새 규칙 위에서 돌아 깔끔하다.

### 7.2 Phase 2~5

| Phase | 내용 | 완료 판정 |
|---|---|---|
| 2 | 컨테이너화 (`Dockerfile`, `.dockerignore`) | 로컬 `docker run` → `/health` 200 · **프론트를 붙여 전 화면 클릭** |
| 3 | HF Space 생성 · 배포 | 공개 URL에서 `/api/recommend` 실제 풀이 성공 |
| 4 | Vercel 환경변수 연결 | 프로덕션에서 성적표 → 추천 전 경로 |
| 5 | 데모 리허설 · 문서 갱신 | `docs/데모_명령어.md` 갱신 · 폴백 절차 실제 수행 |

**Phase 4는 프론트 코드를 수정하지 않는다.** 환경변수만 설정한다(단 `NEXT_PUBLIC_*`은 빌드 타임에
번들에 박히므로 **재배포가 필요**하다). 프론트 수정은 스텝 6.5에서 끝나 있어야 한다.

### 7.3 되돌아갈 지점

Phase 4까지 가도 픽스처 폴백이 살아 있다. 문제가 생기면 `NEXT_PUBLIC_API_BASE`를 지우고
재배포해 1분 내 현 상태로 복귀한다(§3.5-3).

### 7.4 선례

`docs/API_계약.md` 말미에 2026-08-31 기록이 있다 — 이 계약대로 FastAPI 스켈레톤을 작성해
엔드포인트 3개가 전부 동작했고 프론트는 한 줄도 고치지 않았다. 해당 코드는 커밋되지 않아
유실됐으나, **난이도는 이미 검증된 상태**다.

## 8. 한계와 후속

- **영구 저장 없음** — 데모 전제. 실사용자 확대 시 관리형 Postgres(Neon/Supabase 무료 티어)로
  이전한다. 이전 경계는 `recommender/data.py`와 `transcript/load.py` 두 파일에 갇혀 있다.
- **콜드스타트** — 48시간 무활동 후 첫 요청이 느리다. 발표 전날 예열한다.
- **단일 인스턴스** — 수평 확장 시 SQLite가 병목이자 불일치 원인이 된다. 위 이전과 함께 해결.
- **`course_section`의 `source_term`** — 해결됨. `data.active_term()`이 적재된 학기를 DB에서
  읽고, `load_candidates`·`load_section_meta`는 학기를 키워드 인자로 요구한다(기본값 없음).
  두 학기가 함께 적재되면 읽기 시점과 `ingest --validate` 양쪽에서 멈춘다. 다만 **한 번에
  한 학기만** 담는 전제는 그대로다 — 학기 비교·이력 조회를 하려면 이 전제부터 풀어야 한다.
- **졸업요건 적용 범위** — 경영 2022~ · 산데공 2026~ 두 벌뿐이다. 결정 ⑨로 그 이후 학번은
  모두 커버되지만, **경영 2021 이하와 산데공 2025 이하는 거부**된다. 교육과정 개정판이 나오거나
  과거 학번을 지원하려면 책자에서 연도당 10행을 추출해 CSV에 추가한다(크롤러 없음 — 수작업).
- **연도 간 요건 차이 미검증** — 경영은 2022 책자가 이후에도 유효함을 확인했으나, 향후 개정
  여부는 매년 확인이 필요하다. 개정을 놓치면 조용히 틀린 `need_g`가 나간다.
- **PDF 성적표 트랙 미구현** — `transcript/parse.py` 골격만. UI에도 미노출.
