# 학기 갱신 — 2026-1 → 2026-2

추천 결과의 기준 학기를 `2026-1`에서 `2026-2`로 옮긴다.
(2026-09-20 계획 수립. 구현 전.)

`2026-1`이 박혀 있던 것은 크롤 당시 2026-2 분반 계획이 아직 공개되지 않았기 때문이다.
이제 공개되었으므로 갱신하고, **같은 일을 다음 학기에 반복하지 않도록 학기를 인자로 뺀다.**

---

## 1. 목표

| | 지금 | 갱신 후 |
|---|---|---|
| DB `course_section` | `2026-1` 986행 단일 | `2026-2` 단일 |
| 학기 지정 방식 | 크롤러에 상수 하드코딩 | `--term` CLI 인자 |
| 2026-1 데이터 | `data/course_section.csv` | `data/archive/` 보관 |

- **DB에는 한 학기만 둔다.** `ingest.py --reset`이 CSV에서 통째로 다시 굽는 구조라, CSV에 한 학기만
  들어가면 자연히 단일 학기가 된다. 별도 삭제 작업 없음.
- **이전 학기는 코드가 아니라 데이터로 보관한다.** 2026-1을 다시 뽑아야 하면 `--term 2026-1`로 재현한다.

---

## 2. 다시 돌리는 것

순서대로. 앞 단계 산출물이 뒤 단계 입력이다.

```bash
# 1) 분반/시간표 재크롤 → data/course_section.csv
python crawlers/courses/hongik_timetable.py --term 2026-2

# 2) 교시 문자열 → 정수 슬롯 전처리 (time_slots_int)
python crawlers/courses/preprocess_time_slots.py

# 3) 검증 (필드·FK·샘플 기대값)
python crawlers/courses/validate_course_sections.py

# 4) DB 재빌드
python db/ingest.py --reset && python db/ingest.py --validate
```

배포는 추가 작업이 없다. `Dockerfile`이 빌드 타임에 CSV에서 `app.db`를 굽기 때문에,
CSV가 갱신된 채로 재배포하면 그대로 반영된다. 마이그레이션 없음.

## 4. 영향을 받는 곳

### 안 건드려도 되는 것

- **`course` 카탈로그(3,304행)** — 다년도 크롤 보강본이라 학기 무관 마스터다.
- **졸업요건·교육과정** — 입학년도 기준이지 학기 기준이 아니다 (`recommender/data.py:191`).
- **`tests/test_time_slots.py`** — CSV 경로만 참조하므로 새 데이터로 자동 재검증된다.
- **`data/archive/`** — `.dockerignore`가 `data/*` 전체 제외 후 9개 파일만 화이트리스트라 이미지에 안 실린다.

### 확인이 필요한 것

- **학기 선택 드롭다운 표기** — `_extract_option_value`(`hongik_timetable.py:160`)가 라벨을 못 찾으면
  `TimetableCrawlerError`로 죽는다. 첫 실행에서 바로 드러난다.
- **교양 스코프 코드** — `LIBERAL_ARTS_SCOPES`/`ENGINEERING_LIBERAL_ARTS_SCOPES`(`:87-131`)의
  `p_grade` 값은 주석에 명시된 대로 *2026-1 페이지 기준 관측치*다. 학기마다 바뀔 수 있으므로
  크롤 후 스코프별 행수를 2026-1과 대조한다. **0행짜리 스코프 = 코드가 바뀐 것.**
- **교시 상한** — `preprocess_time_slots.py:55`의 `MAX_PERIOD = 13`은 2026-1 관측 최대치이고 fail-loud다.
  2026-2에 14교시가 있으면 `ValueError`로 멈춘다. 이 동작은 **그대로 둔다** — 조용히 통과하는 것보다 낫다.

### 조용히 틀릴 수 있는 것 ⚠️

**2026-2 신규 개설 과목의 역량 매핑.**

현재는 `course_competency`가 3,304과목을 100% 덮고 있어 누락이 없다. 2026-2에만 있는 신규
`course_id`가 들어오면:

- `course`에 없으면 → **FK 위반으로 적재 실패.** 시끄럽게 죽으니 놓칠 일은 없다.
  (`crawl_catalog.py --from 2020 --to 2026` 재실행으로 카탈로그 보강)
- `course_competency`에 없으면 → **적재는 되지만 `w_{c,k}`가 없어 ILP 후보에서 조용히 탈락한다.**
  에러도 경고도 없이 그 과목만 절대 추천되지 않는다. 이쪽이 위험하다.

## 5. `source_term` 필터

`recommender/data.py:98-108`의 후보 쿼리에는 학기 필터가 없다.
`course_section`의 PK가 `(course_id, section, source_term)`(`db/schema.sql:150`)이라
두 학기가 같이 적재되면 같은 과목이 중복 후보로 들어간다.

이번 방식(CSV 단일 학기 + `--reset` 재빌드)에서는 DB에 한 학기만 남으므로 실제 문제가 되진 않는다.
그래도 필터를 넣는다 — 세 줄이고, `docs/배포_설계.md` §8에 후속 과제로 적혀 있던 항목을 여기서 닫는다.
나중에 누가 두 학기를 같이 적재해도 조용히 망가지지 않게 된다.

---

## 6. 미정

**신규 과목 역량 매핑을 어떻게 처리할지**는 크롤 전에 정할 수 없다. 신규 `course_id`가 몇 개인지
알아야 판단이 서기 때문이다. 그래서 순서를 이렇게 잡는다:

1. 크롤 → `data/course_section.csv` 생성
2. `course`(3,304행) 대비 신규 `course_id` 개수를 센다
3. **0개면** 매핑은 손대지 않고 그대로 진행
4. **있으면** 개수를 보고 증분 실행 / 전량 재실행 / 이번엔 생략 중에서 결정

참고로 2026-1은 280개 `course_id` 전부가 `course`에 존재해 FK 위반이 0이었다.
